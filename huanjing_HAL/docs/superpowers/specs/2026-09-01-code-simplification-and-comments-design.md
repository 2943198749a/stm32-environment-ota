# STM32 FreeRTOS 环境监测工程整体精简与详细注释设计

## 1. 背景

当前工程包含 STM32F103、FreeRTOS、LCD、DHT11、BH1750、MQ135、ESP32 串口网关、华为云通信、Bootloader 和 A/B 分区 OTA。功能已经较完整，但应用层存在重复代码、历史接口、职责混杂、测试与当前实现不同步、OTA 源码双份维护等问题。

本次重构的目标不是尽可能减少文件或代码行数，而是在完全保留现有功能、硬件行为和通信兼容性的前提下，让初学者能够更快理解模块边界、主流程和关键安全约束。

## 2. 目标

1. 保留全部现有功能和硬件行为。
2. 减少重复分支、无效计算、历史接口和多处维护点。
3. 让 FreeRTOS 任务循环只表达清晰的业务步骤。
4. 让 UART 接收只有一个明确的数据消费路径。
5. 保持 OTA 协议、状态机和 Flash 写入流程可逐步调试。
6. 为项目自写代码增加面向初学者的详细中文注释。
7. 更新自动化测试，使测试反映当前四任务、双页面和完整 OTA 功能。
8. 建立主工程 OTA 源码与便携发布副本的一致性检查。

## 3. 非目标

本次不进行以下修改：

- 不修改 STM32 HAL、CMSIS 或 FreeRTOS 内核源码。
- 不改变 MCU 型号、时钟树、GPIO、UART、I2C、ADC 或 FSMC 配置。
- 不改变任务数量、优先级、栈大小和运行周期，除非验证证明当前配置无法安全运行。
- 不改变 LCD 页面功能、按键映射和用户可见信息。
- 不改变 STM32 与 ESP32 之间的文本或二进制协议。
- 不改变 Bootloader、A/B 分区地址、分区容量、元数据格式或升级确认规则。
- 不将明确的 OTA 状态机改成通用框架或高度抽象的解析器。
- 不在没有版本控制和恢复路径的情况下删除 Keil 配置、构建产物、生成文档或临时文件。

## 4. 修改边界

主要修改范围：

- `Core/Src` 与 `Core/Inc` 中的项目自写应用模块。
- `user/OTA/Src` 与 `user/OTA/Inc` 中的 OTA 业务代码。
- `tests` 中与当前应用结构和 OTA 逻辑相关的测试。
- `portable_ota/stm32/ota_core` 中由主工程 OTA 源码导出的便携副本。
- 与变更直接相关的 Markdown 说明文档。

CubeMX 生成文件只修改 `USER CODE` 区域，除非某项必要修复无法在用户代码区完成。任何例外都必须在实施记录中单独说明。

## 5. 注释标准

详细注释以帮助初学者理解为目标，但必须服务于代码，而不是复述代码。

### 5.1 文件头注释

每个项目自写模块说明：

- 模块负责什么。
- 模块不负责什么。
- 上层如何调用。
- 依赖哪些硬件或其他模块。
- 是否由中断和任务并发访问。

### 5.2 公共接口注释

每个公共函数在头文件中说明：

- 输入参数的单位、有效范围和空指针规则。
- 返回值代表什么。
- 调用前置条件。
- 是否允许在中断中调用。
- 是否可能阻塞以及最长等待时间。
- 共享数据的所有权和生命周期。

### 5.3 关键实现注释

实现文件重点解释：

- FreeRTOS 临界区为什么足够，以及为什么绘制 LCD 时不能持有临界区。
- 为什么传感器初始化必须在调度器启动后的任务中执行。
- UART 环形缓冲区的读写指针、满缓冲区处理和中断约束。
- OTA 帧每个字段的字节序、长度、CRC 范围和 ACK/NACK 规则。
- Flash 擦除、写入、校验、pending 和确认的先后关系。
- A/B 分区升级中禁止覆盖当前运行分区的原因。
- LCD 局部刷新、缓存旧值和避免闪烁的关系。
- 传感器有效标志与 `NO DATA` 显示的关系。

### 5.4 不添加的注释

不添加以下低价值注释：

- 复述变量赋值或简单 `if` 条件。
- 与代码不一致的历史故事。
- 可以由清晰函数名直接表达的操作说明。
- 大段被注释掉的旧代码。
- 无法由测试或实现验证的承诺。

## 6. FreeRTOS 应用结构

保留当前四个任务：

1. 传感器任务负责初始化和周期采样。
2. UI 任务负责按键和 LCD 刷新。
3. 遥测任务负责构造并发送 `ENV` 文本。
4. OTA 任务负责解析网关数据和确认新固件。

任务入口不承担复杂格式化或重复校验。通过文件内静态辅助函数表达以下步骤：

- 判断一帧环境数据是否完整有效。
- 格式化带一位小数且支持负数的温度。
- 构造并发送一行环境遥测数据。
- 检查全部任务句柄是否创建成功。
- 判断新固件是否到达确认时间并发送 `BOOT_OK`。

环境数据仍使用结构体副本和极短临界区共享。传感器任务写入共享副本，UI 与遥测任务复制到局部变量后再处理。LCD 绘制、`snprintf` 和 UART 发送不得在临界区内执行。

## 7. ESP32 UART 数据路径

USART2 的唯一底层接收路径为：

```text
UART 接收中断 -> 环形缓冲区 -> OTA 任务按字节读取 -> 文本或二进制协议解析
```

保留接口：

- 初始化软件缓冲区并启动首次中断接收。
- 发送文本。
- 从环形缓冲区读取一个字节。
- HAL UART 接收完成回调。

全工程确认无生产调用后，删除旧的独立行缓冲、`Esp32Uart_Process()` 和 `Esp32Uart_ReadLine()`。`STATUS` 行由 OTA 串口解析器在非升级状态下转发到网关状态模块。这样可以避免两个解析器竞争同一个环形缓冲区。

环形缓冲区满时继续采用丢弃新字节的策略，不改变现有协议行为。中断中只保存字节并重新开启接收，不执行格式化、LCD、Flash 或日志操作。

## 8. LCD UI 精简

保留环境仪表盘和系统状态页，保留现有颜色、坐标、提示、OTA 进度和局部刷新。

精简方式：

- 使用枚举表示当前页面。
- 提取统一的卡片值写入和无数据显示逻辑。
- 将温度、湿度、光照和空气质量的格式化保留为清晰的小函数。
- 保留旧值缓存，只在页面重绘或数据变化时操作 LCD。
- 不使用复杂函数指针、无类型数据表或宏元编程压缩代码。

UI 模块继续只负责显示，不直接读取传感器、UART 或 Flash。

## 9. OTA 串口状态机精简

保留显式枚举和 `switch` 状态机，状态仍包括同步字节、序号、长度、负载和 CRC 的逐段接收。

允许的精简：

- 删除计算后立刻被覆盖的 CRC 临时逻辑。
- 提取 ACK/NACK 响应构造。
- 提取重复的中止、复位帧状态和错误消息处理。
- 减少深层嵌套，但不合并具有不同安全含义的错误分支。
- 用具名常量和注释说明帧格式、长度限制和小端序。

必须保持：

- 同步字节、帧头、序号、长度、负载和 CRC 的格式。
- CRC16 算法和覆盖范围。
- 偶数字节写入约束。
- 分片最大长度。
- `OTA_READY`、`OTA_ACK`、`OTA_NACK`、`OTA_OK` 和 `OTA_ERROR` 文本。
- `OTA_BEGIN`、`OTA_END` 与 `OTA_ABORT` 行为。
- SHA-256、镜像长度、目标槽位和版本号校验。

## 10. OTA 源码唯一维护源

`user/OTA` 是主工程实际编译的维护源。`portable_ota/stm32/ota_core` 是可独立拷贝的发布副本。

由于发布副本必须自包含，物理重复文件保留，但手工双份维护被取消：

- 所有通用 OTA 修改先发生在 `user/OTA`。
- 使用脚本同步通用文件到 `portable_ota/stm32/ota_core`。
- 使用测试比较对应文件哈希。
- 明确允许与目标平台有关的端口适配文件不同。
- 发布说明标记便携目录为导出副本。

## 11. 测试策略

测试先于生产重构更新，以便测试能够描述当前真实行为。

需要修正：

- 当前任务数量为四个，并检查四个任务句柄。
- `AppUi_Render()` 同时接收环境数据与 ESP32 状态。
- 第二页是系统与 OTA 状态页，不再是旧版静态占位页。
- UART 公共接口以字节读取路径为准。
- FreeRTOS 堆容量测试统计四个任务栈。

需要保留或新增：

- 传感器初始化位于任务内部。
- GPIO、I2C、ADC 和 UART 外设配置存在。
- 环境数据有效标志控制显示与上传。
- 任务创建失败进入错误处理。
- CRC 已知向量和 OTA 帧构造/验证测试。
- STATUS 行的合法、越界、缺字段和超长消息测试。
- OTA 通用源码与便携副本一致性测试。
- 项目自写头文件公共接口注释覆盖检查。

如果本机存在可用 ARM/Keil 工具链，则执行完整编译。否则执行全部 PowerShell 测试、主机 C 测试、静态引用搜索，并明确记录未执行的硬件构建验证。

## 12. 实施顺序

1. 建立当前基线并记录哪些旧测试失效。
2. 更新测试，使其描述当前功能，而不是旧版三任务和 OTA 占位设计。
3. 精简 UART 单一接收路径。
4. 精简 FreeRTOS 任务入口和公共辅助逻辑。
5. 精简 LCD UI 重复显示逻辑。
6. 精简 OTA UART 状态机中的明确重复和无效代码。
7. 补齐项目自写模块的文件、公共接口和关键实现注释。
8. 同步便携 OTA 副本并执行一致性检查。
9. 运行全部可用测试和构建验证。
10. 检查代码尺寸、RAM/栈配置、警告和行为兼容性。

## 13. 完成标准

只有同时满足以下条件才算完成：

- 传感器、LCD、按键、ESP32 状态、环境上传和 A/B OTA 功能路径仍然存在。
- 四个任务的优先级、栈大小和周期没有未经说明的改变。
- 串口文本与二进制协议保持兼容。
- Flash 布局、元数据和升级确认规则保持兼容。
- 项目自写代码的模块职责和公共接口具有详细中文注释。
- 明确重复、无效计算和无生产调用的历史 UART 行接口已被处理。
- 更新后的自动化测试全部通过。
- 可用工具链下的工程构建通过且没有新增警告。
- 主工程 OTA 通用源码和便携副本通过一致性检查。
- 第三方代码、无关生成文件和用户配置没有被意外修改。

## 14. 风险与控制

- **实时性风险：** 不增加锁持有时间，不在临界区内格式化、绘图或发送。
- **UART 丢包风险：** 不改变中断接收、缓冲区大小和消费周期；删除旧接口前执行全工程引用检查。
- **OTA 兼容风险：** 使用已知帧测试和协议字符串测试保护字节级兼容性。
- **Flash 安全风险：** 不重写存储布局或升级事务，只整理重复控制逻辑。
- **CubeMX 覆盖风险：** 优先只改 `USER CODE` 区域，并记录必要例外。
- **缺少版本控制风险：** 不删除材料性文件；每轮修改保持小范围并在验证后继续。
